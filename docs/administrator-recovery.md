# Administrator MFA and recovery

Run the normal migration command before serving the updated console. PHP sodium
is required. Keep SESSION_SECRET stable and private: it now also protects encrypted
authenticator seeds. Losing or changing it requires operator recovery for enrolled
accounts. Back up the key separately from the database, using your secret manager.

After applying migration 012, an operator must upgrade an existing restricted
runtime role before starting the updated application:

```sql
GRANT SELECT, INSERT, UPDATE ON `YOUR_SCHEMA`.`admin_security` TO `novikov_runtime`;
```

Substitute the actual schema and role; apply this using the provisioning account,
not the web runtime. These are the only new table privileges required; UPDATE
also permits the locking reads used to serialize one-time code consumption.
Do not grant DELETE, DDL or administrative privileges. New roles generated by
`php novikov/bin/runtime-grants.php YOUR_SCHEMA NEW_ROLE` include this grant.
The generator deliberately refuses to recreate an existing role; do not drop
an existing role to upgrade it. Inspect SHOW GRANTS and follow
`docs/database-permissions.md` for role assignment and activation.

Every administrator, including existing accounts, must confirm authenticator
enrollment after password verification before obtaining console access. Existing
password-only sessions are rejected. The enrollment screen supplies a manual setup
key (SHA-1, six digits, 30-second TOTP). Challenges last five minutes; codes allow
one time step of clock drift and cannot be replayed. Synchronize server clocks.
Ten random, single-use recovery codes are shown once after enrollment. Save them
privately; they are never recoverable from the stored hashes. A recovery code
replaces only the second factor, not the password.

## Operator-assisted recovery

There is no public reset email endpoint and no default credential. A server
operator with protected shell and database access runs:

```
php novikov/bin/recover-admin.php
```

Use a private interactive terminal, not CI or a recorded/shared console.
Independently verify the owner's identity against your established organizational
records and a known communication channel. Never rely solely on the email address
or a message requesting recovery. Record approval in your incident/ticket process;
enter only its non-sensitive reference in the tool.

Authorization immediately revokes all sessions and pending challenges and blocks
password sign-in. Privately deliver the displayed token to the verified owner,
who submits it at `/recovery` with their email and a new password of at least 16
characters. Never put the token in a URL, ticket, log or command argument.
The token lasts 15 minutes and can be used once. If it expires or is lost, rerun
the operator tool after checking identity again; issuance replaces the old token.
An expired authorization intentionally does not unlock the potentially compromised
account. Successful recovery revokes the old password, authenticator, codes and
sessions; the owner must sign in and enroll a new authenticator.

Failed attempts are limited persistently in the database. Password and MFA account
limits are five attempts per 15 minutes; recovery also has a source limit. This can
temporarily lock legitimate users out: wait for expiry rather than deleting limits
on an unverified caller's request. Audit records contain security events and the
approval reference, never passwords, codes, seeds or recovery tokens.

## Verification

Use a disposable MySQL server with CREATE/DROP DATABASE permission:
`php novikov/tests/admin-auth.php` and `php novikov/tests/admin-mfa.php`.
These generate random test credentials and drop their isolated schemas.
The MFA suite also needs CREATE USER/ROLE authority for setup; all authentication
and recovery operations run through a separate connection bearing only the
generated restricted runtime role. It checks that destructive MFA-table privileges
are denied, and removes the temporary user and role afterward.
Do not grant schema-creation privileges to the production runtime account.
Real-money deposits, investments and withdrawals remain disabled independently.
